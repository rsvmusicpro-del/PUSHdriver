# PUSHdriver project context

This is the durable project hand-off for future work. It summarizes the intent,
compatibility constraints, current architecture and verification boundaries
established on branch `custom`.

## Project objective

PUSHdriver is a Push 1-only Bitwig controller extension, adapted from the
DrivenByMoss framework. The work is not to create a new DAW or a second
controller implementation. It is to preserve the upstream controller's
existing modes, views, commands, mappings and framework behavior while
adapting the Push 1 workflow to the Bitwig API version targeted by the project.

The intended compatibility target is:

- Original Ableton Push 1 hardware and its USB-MIDI protocol.
- Bitwig Studio 4.3.10.
- Bitwig Extension API 17.
- Java 17.
- Pinned DrivenByMoss 19.2.2 source at
  `013620c1330cdcf896e96ef8fdc8a2123e4fce6a`.

The build assembly is generated by `scripts/prepare_push1.py` from the pinned
`upstream/` submodule plus the project-owned `overrides/java/` sources.
Push 2 USB/HID display code and unrelated controller implementations are
excluded from the packaged extension.

## Working rules

- Target only the protected Git branch `custom`; inspect its history before
  making changes. Because branch protection now requires pull requests, propose
  changes through a short-lived PR branch targeting `custom`. Never modify
  `main`.
- Preserve the upstream source pin and API 17 compatibility.
- Keep production behavior changes separate from test infrastructure.
- Prefer small, regression-backed changes to production commands and modes.
- Do not claim a physical hardware test, Bitwig host test or pixel-accurate
  display certification when only virtual tests have run.
- The virtual bench must remain independent of a physical Push, native MIDI
  drivers and a running Bitwig Studio process.

## Functional scope already adapted

The branch history records work on Push 1-specific navigation and Shift page
semantics, In/Out device/browser navigation, New clip behavior, Note/Session
workflows, Drum/Drum64 note behavior, sequencer page-follow and playhead
safety, Note Repeat guards, LED color behavior, firmware inquiry parsing,
Linux MIDI discovery, and fixed-width LCD safety. The existing DrivenByMoss
controller setup, views, modes and production commands remain the behavior
under test.

## Autonomous verification architecture

The virtual bench has three layers:

1. `VirtualPush1Device` models the Push 1 MIDI surface and feedback state:
   pads, pressure/aftertouch, buttons, encoders, touch events, ribbon,
   pitch-bend, LEDs, RGB pad SysEx and LCD SysEx.
2. `VirtualPush1MidiBench` substitutes API-17 `IMidiInput` and
   `IMidiOutput`, dispatching events through registered hardware bindings
   and routing extension feedback to the virtual device.
3. `VirtualPush1RuntimeTest` boots the assembled production
   `PushControllerSetup` with deterministic API-17 host/model collaborators
   and exercises real registered commands and modes.

The MIDI bench forwards pad note-on/note-off to the active production view's
`onGridNote` and poly-aftertouch to its registered aftertouch command. It also
captures the MIDI output produced by those commands. This ensures that pad
protocol serialization and actual view handling are tested as separate layers.

The acceptance inventory covers the Push 1 setup's 50 registered modes and 14
packaged views, plus protocol-exhaustive pad, encoder, ribbon, LED and LCD
checks. Stateful scenarios exercise Browser, New Clip, Note Repeat,
Sequencer/Poly Sequencer, Drum 4/8/64, Device bank boundaries, empty device
layers, transport and aftertouch. The exact list of assertions is maintained in
`docs/VIRTUAL-PUSH1-COVERAGE.md`.

The protocol and runtime tests run in CI without a physical controller or a
Bitwig process. The host/model collaborators are deterministic API-17 proxies,
not a complete reimplementation of Bitwig's internal engine. This proves the
tested controller-side contract, not every undocumented Bitwig behavior.

## Push 1 display construction contract

The Push 1 is not a Push 2-style pixel display. Its text display consists of
four physical LCD modules arranged horizontally:

- 4 physical modules, ordered left to right.
- Each module: 4 rows × 17 character positions.
- Combined logical display: 4 rows × 68 character positions.
- Each row has 8 logical cells with alternating widths
  9, 8, 9, 8, 9, 8, 9, 8.
- Each 17-character module/block corresponds to two adjacent logical cells.
- LCD output is one 77-byte SysEx frame per row, with row selectors
  `18` through `1B`, 68 seven-bit character bytes and `F7`.
- Push-specific glyph values must remain intact as raw seven-bit character
  codes; converting them to ordinary ASCII is only suitable for a text
  diagnostic view, not for the hardware output.
- The eight programmable glyphs at character codes 0–7 have extracted 5 × 8
  dot-matrix data in `Push1DisplayGlyphs`; the virtual device exposes those
  bitmaps for pixel-level assertions. Standard ROM glyphs remain firmware-owned.

`Push1DisplayLayout` is the single source of truth for module count,
dimensions, global and module-local columns, block positions, logical cell
offsets and cell widths. The production `Push1Display` assembly and
`VirtualPush1Device` use the same geometry. Tests must cover the complete
4 × 68 character map, all module boundaries, all logical cells and custom
glyph preservation.

No authoritative physical pixel width, glass dimensions, module spacing or
LCD controller revision is available in the project's current protocol
sources. Do not invent pixel or millimetre measurements. A later bitmap
renderer may use documented/reverse-engineered 5 × 8 glyph patterns, but it
must keep physical dimensions clearly marked as unknown unless an authoritative
hardware source is found.

## Interactive virtual Push 1 desktop simulator

`tests/java/VirtualPush1Simulator.java` provides an optional Swing front end
for the same `VirtualPush1Device` and `VirtualPush1MidiBench` used by the
production runtime regression. It is opened from
`VirtualPush1RuntimeTest` with the `--gui` argument; the normal headless CI
path does not create a window.

After building the extension and ensuring the Bitwig API 17 JAR is in Maven's
local repository, launch it with:

```sh
python3 scripts/test_push1_extension.py --gui
```

The window exposes all 64 pads (mouse press/release, adjustable velocity 1–127), a
selectable held-pad aftertouch slider, momentary Push buttons and Shift chords,
nine main and two small encoders (step controls plus independent touch
switches), Ribbon touch and 14-bit position, and the eight bottom-row RGB
controls. It renders the four physical LCD modules as 4 × 17 character
segments and refreshes pad/button LED feedback from the virtual device. Hovering
LCD rows reveals raw character codes and the extracted custom 5 × 8 glyph
bitmaps. The MIDI monitor displays device-to-controller messages, controller output and
host raw MIDI output.

This is a controller-side interactive test surface, not a DAW UI: the runtime
still uses deterministic Bitwig API-17 host/model proxies. It does not create
an OS-level virtual MIDI port, attach to an external Bitwig process, or
certify physical Push USB, pressure calibration or LCD glass appearance.

## CI and known validation boundary

The GitHub Actions workflow builds and validates Linux and Intel macOS with
Java 17, runs the Push 1 protocol/display/runtime acceptance suite, packages
the API-17 extension and enforces a combined `quality-gate` job. Branch
`custom` is protected and requires `quality-gate` before a pull request can
merge. The detailed coverage inventory and explicit validation boundaries are
tracked in `docs/VIRTUAL-PUSH1-COVERAGE.md`. Protocol regressions cover every
valid pad velocity and pressure value on all 64 pads, all signed relative-step
values on all 11 encoders, and all 16,384 ribbon positions.

A successful CI run does not itself launch Bitwig Studio 4.3.10, emulate the
Bitwig scheduler/model in full, test native MIDI port discovery on every
machine, or measure physical pad/pressure/USB timing. Those are explicit
limits, not reasons to make physical hardware a dependency of ordinary
development and regression testing.
